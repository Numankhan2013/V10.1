# V11.7 Cross-device QBank

## Architecture

V11.7 keeps the accepted application and question bank as the product core:

```text
bundled/generated QBank HTML + static medical content
                    |
          +---------+---------+
          |                   |
Android WebView APK      responsive PWA
          |                   |
          +------ Firebase ---+
                 user state
```

Questions, PDFs, source visuals, renderers, navigation, Practice, CBT, Review,
Insights, and Custom Study Modules are still generated by the existing
deterministic pipeline. Firestore contains private learner state, not a second
question database.

Android serves bundled assets from `https://qbank.local/app/` so secure HTTPS
Firebase requests work without enabling WebView universal file access. On the
first V11.7 launch, `migrate_local_state.html` reads the prior `file://`
localStorage and a narrow native bridge imports it into the new origin before
the app boots. The bridge is then removed. A second backup,
`qbank_state_pre_cloud_v1`, is created before the first cloud merge.

## Synced model

All documents live below `users/{uid}`. The committed rules permit an
authenticated user to access only their own subtree and reject arbitrary
fields, oversized payloads, physical deletes, or a schema version other than
the supported one.

| Collection | Identity and merge behavior |
| --- | --- |
| `attempts` | Immutable attempt ID; union and deduplicate |
| `tests` | Stable test/session-result ID; latest revision if repeated |
| `bookmarks` | Question ID; last-write-wins event with deletion tombstone |
| `modules` | Module ID + restart epoch; same-epoch completed questions merge, latest metadata wins |
| `sessions` | `active`; newest revision wins |
| `preferences` | `main`; newest revision wins |

Every cloud document also records `ownerDevice`, `updatedAt`, `deleted`, and
`schemaVersion`. Device-specific document IDs prevent two devices from
overwriting each other's revisions. Each sync pulls cloud revisions first,
compares pending local envelopes, merges deterministically, and only then
uploads changed local entities. Simply opening an older device therefore does
not stamp its old snapshot over a newer one. Attempts and completed tests are
additive; bookmark/module deletion uses tombstones. Review schedules, streaks,
wrong-question state, topic performance, and Insights are rebuilt from the
merged canonical attempts instead of being maintained as divergent analytics.

The outbox and cursors live in `qbank_sync_v1`. A save writes local QBank state
and the outbox synchronously; network transfer is debounced. Offline work stays
available immediately and uploads after the `online` event or **Sync now**.

## Firebase setup (one-time account action)

1. Create a Firebase project on the Spark plan.
2. Enable Authentication → Sign-in method → Email/Password.
3. Create the default Cloud Firestore database. Choose a region close to the
   devices; changing it later is not trivial.
4. Install/authenticate the Firebase CLI and deploy the committed rules:

   ```sh
   firebase use YOUR_PROJECT_ID
   firebase deploy --only firestore:rules
   ```

5. In GitHub repository **Settings → Secrets and variables → Actions →
   Variables**, add:

   - `QBANK_FIREBASE_API_KEY`
   - `QBANK_FIREBASE_PROJECT_ID`
   - `QBANK_ANATOMY_PDF_URL` (described below)

Firebase web API keys are public project identifiers and belong in runtime
configuration; they are not privileged service credentials. Privacy comes from
Authentication plus `firestore.rules`. Do not add service-account keys to the
client or repository.

For a local configured build, set the same environment variables and run:

```sh
python3 tools/write_runtime_config.py
```

With no configuration, Android and the PWA remain fully local-first and the
More screen clearly reports that sync is disabled.

## Cloudflare Pages and Anatomy source PDF

The workflow creates `build/web` and uploads it with the APK as the
`V11.7-android-pwa` artifact. If Cloudflare credentials exist, the same job
deploys that exact verified directory.

Create a Pages project and add GitHub Actions secrets:

- `CLOUDFLARE_API_TOKEN` with Pages edit permission
- `CLOUDFLARE_ACCOUNT_ID`

Optionally add `CLOUDFLARE_PAGES_PROJECT`; it defaults to `nk-qbank`.

Cloudflare Pages rejects individual assets larger than 25 MiB. The Anatomy PDF
is about 46 MiB, so `build_web_dist.py` deliberately excludes it rather than
letting deployment fail. Upload the unchanged `Anatomy_QBank_Source.pdf` to a
public Cloudflare R2 bucket (or a custom-domain R2 public URL), configure CORS
to permit the Pages origin and byte-range GET requests, and set that URL as
`QBANK_ANATOMY_PDF_URL`. Biochemistry and Physiology PDFs remain below the Pages
limit and ship in the PWA artifact. Browser source solutions are rendered
locally with the vendored Mozilla PDF.js build; Android continues to use native
`PdfRenderer`.

## PWA behavior

- Manifest, 192/512 icons, standalone display, Apple Home Screen metadata.
- iPad/tablet side navigation, wider study layouts, two-column module topic
  selection, and landscape question/navigation panels; phone styling remains
  unchanged below 768 px.
- Shell and static QBank data cached on install; generated source visuals and
  PDFs cached when used. Firebase calls remain network-bound and feed the local
  outbox when offline.
- `index.html`, runtime config, and the service worker use no-cache headers so
  a deployment can update promptly; fingerprint-stable assets use runtime
  caching.

On iPad: open the HTTPS Pages URL in Safari, use **Share → Add to Home Screen**,
then launch NK QBank from its icon.

## Verification checklist

Automated gates cover JavaScript syntax, state merge/deduplication, stale
bookmark/session protection, same-epoch module progress union, review rebuild,
security-rule ownership markers, PWA files, generated app contracts, packaged
APK checks, and web artifact generation.

External end-to-end acceptance still requires configured accounts:

1. Upgrade an Android installation with existing progress and confirm all local
   attempts, bookmarks, tests, and modules remain.
2. Sign in on Android; answer and bookmark questions; use **Sync now**.
3. Sign in to the installed iPad PWA and confirm the same state and in-progress
   module/session.
4. Make changes on iPad, synchronize, and confirm Android receives them.
5. Work offline on one device, reconnect, and confirm additive attempts plus
   newest bookmark/session behavior.
6. Force-close/reopen both targets; test sign-out/sign-in and a fresh second
   device.
7. Inspect the major screens at phone portrait, iPad portrait (768×1024), iPad
   landscape (1024×768), and a desktop width.

Do not label V11.7 device-verified or accepted until these checks are performed.
